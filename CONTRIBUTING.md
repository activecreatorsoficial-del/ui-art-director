# Contributing

Help the skill make better decisions across different products. A useful change has an observable motivation, a focused instruction update, and evidence that it does not merely impose one aesthetic everywhere.

## Report an issue

Include the task and desired outcome, skill revision, model and tools if known, platform and stack, shareable starting artifacts, what actually happened, and why the outcome failed. Screenshots are useful when accompanied by viewport, state, and interaction context. Redact private information and confirm that any assets can be shared.

Distinguish a routing failure, design mismatch, implementation defect, unavailable tool, and personal preference. Explain the context in which a preference matters.

## Propose a change

1. Keep the core entrypoint concise and move substantial conditional guidance into a relevant reference.
2. Preserve user scope, existing brands, framework choices, and permissions. Add no silent external action or globally installed skill rewrite.
3. Avoid fixed aesthetic presets, invented quality scores, and claims of universal expertise.
4. Update or add an evaluation case when the change affects behaviour. Compare baseline and candidate on equivalent starting artifacts when feasible, including an unrelated context for broad changes.
5. Run the checks described in [README.md](README.md), report their actual result, and explain any behavioural evaluation that remains unperformed.

Use the same language and intent in both READMEs when changing installation or user-facing behaviour. Bump the version in the skill metadata for a release; maintainers decide release timing. Do not add dependencies or scripts to the installed skill without a concrete need.
